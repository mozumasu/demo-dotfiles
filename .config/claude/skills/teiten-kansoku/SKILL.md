# 定点観測会の資料を作る

週1回の定点観測会で使う資料の下書きを、Markdown で作る。会議では、この資料を見ながら宿題の結果を確かめ、アラートの対応と担当を決める。

## 設定ファイル

組織やプロダクトに固有の値は、この skill には書かず `~/.config/teiten-kansoku/config.md` に置く。最初にこのファイルを読む。ファイルがなければ、下の項目を利用者に聞いてから作る。

- 監視サービスとアカウント ID、データの取り方（MCP、CLI、API など）
- 表のリンク先にするダッシュボード
- 調べるリポジトリ（アプリ、インフラ、マニフェスト）
- 環境の名前（本番、検証など）
- 議事録の置き場所と、前回の議事録の探し方
- 共有先のチャットのチャンネル

## 手順

1. **前回の議事録を読む**: 宿題と「対応を決めたいこと」を拾う。議事録を読めないときは、利用者に貼ってもらう。
2. **宿題の結果を調べる**: 項目ごとに、関係する Issue や PR の状態と、アラートの件数の変化を確かめる。
3. **アラートを集計する**: 直近7日と、その前の7日を集計する。期間は実行時刻から数え、資料には JST で書く。
4. **注目アラートを選ぶ**: 今週初めて鳴った条件と、先週の2倍以上に増えた条件を選ぶ。どちらもなければ、件数が最も多い条件を選ぶ。
5. **原因を調べる**: 注目アラートごとに、ログ、トレース、条件の定義、リポジトリのコードとマニフェストを見る。
6. **下書きを出す**: 下の型で Markdown を出す。利用者が頼んだときだけ議事録に書き込む。

## 資料の型

```markdown
# 定点観測会 YYYY-MM-DD

## 宿題
前回: （前回の議事録へのリンク）
- （宿題）→ （日付）完了／調査中。（結果を1〜2文）（Issue・PR の番号）

## 1. 今週のアラート一覧（MM-DD 〜 MM-DD）
直近7日の incident は N件 / N条件（先週 N件 / N条件）。有効な条件は N本あるので、鳴ったのは N本（N%）。（増減の主な理由を1文）

| 条件 | incident | 先週 | 平均継続 | 発生時刻（JST） | 環境 | ダッシュボード |
|---|---|---|---|---|---|---|

- 先週鳴って今週ゼロ: （条件と先週の件数）
- 今週初登場: （条件）
- 時刻の傾向: （毎日同じ時刻に鳴る条件と、その中身）
- ほかに気づいたこと: （無効になった条件、見つからないダッシュボードなど）
- 集計: （使ったデータと期間、条件数の数え方）

## 2. 注目アラートの原因と対策
対象: （選んだ理由）

| 条件 | 件数 | 結論 | ユーザー影響 | 対応の優先度 |
|---|---|---|---|---|

### （条件名）（N件）
- 結論: （1文）
- 証拠: （時刻、件数、ログの中身）
- 仕組み: （なぜ鳴るか。ファイルと行番号）
- 影響: （利用者にどう見えるか）
- 対策案: （複数あれば並べる。先に確かめることも書く）

## 対応を決めたいこと
- （論点）: （選択肢）。誰がやるか

## 集計に使ったデータ
（データの種類、確認したリポジトリとブランチ）
```

## 書き方のルール

- 事実の記述には、末尾に（確認済み）か（推測）を付ける。データやコードで確かめたことだけを（確認済み）にする。
- 時刻は JST で、`10/15(木) 09:54` の形で書く。
- 件数がサンプリングを受けたデータなら、そのことと、どこまで使えるか（割合や順位は使える、など）を書く。
- 1回だけの利用者の操作で鳴ったアラートは、条件の窓や件数の下限の見直しを対策案に入れる。
- 宿題は消さずに残し、結果を追記する。終わっていない宿題は「対応を決めたいこと」にも載せる。
- 原因が分からないものは「未特定」と書き、次に見ることを並べる。
- 対応と担当は会議で決めるので、資料では決めない。
